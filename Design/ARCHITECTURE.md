# Leo Game — Architecture & Coding Rules (v0.1)

> Черновая версия. Свод правил для масштабирования и поддержки проекта — фиксируется и дополняется итеративно, по мере роста кодовой базы. Правила должны быть конкретными и проверяемыми на реальном коде проекта, а не абстрактными формулировками "из учебника".

## 0. Зачем это нужно

`PlayerController.cs` уже вырос до ~380 строк и совмещает: движение, дэш, ближний бой, дальний бой, анимации, HUD-обновления, обработку паузы и респавн по сохранению. Это рабочий код, но он же — наглядный пример, почему нужны правила: без них каждый новый фиче (враги, боссы, progression) будет добавляться в тот же файл или тем же стилем, и сложность будет расти быстрее, чем объём фич.

Правила ниже — не самоцель "написать по SOLID", а конкретные приёмы, которые держат код изменяемым: новый враг/оружие/способность добавляется, не трогая существующий рабочий код и не разрастая существующие классы.

## 1. Общие принципы (SOLID → Unity/C#)

### 1.1 Single Responsibility — один MonoBehaviour, одна причина для изменений
Компонент должен отвечать за одну зону геймплея. Если у класса появляются несвязанные друг с другом группы полей и методов (как сейчас в `PlayerController`: движение / бой / HUD / сохранение) — это сигнал разделить его на несколько компонентов на одном GameObject, общающихся между собой (см. 3.2).

**Практическое правило:** если для описания класса в одном предложении нужен союз "и" ("двигает персонажа **и** стреляет **и** обновляет HUD") — разделять.

### 1.2 Open/Closed — новый контент без правки существующего кода
Новый враг, оружие или способность должны добавляться **новым файлом/ассетом**, а не веткой `if` внутри существующего класса. Практически это значит:
- Полиморфизм через интерфейсы (`IDamageable` — уже пример) вместо `if (enemy.type == EnemyType.Drone)`.
- Настраиваемые параметры (урон, скорость, кулдауны) выносятся в данные (ScriptableObject/сериализуемые поля), а не в новую ветку кода под каждого врага.

### 1.3 Liskov Substitution — наследники не удивляют
Если появится базовый класс `EnemyBase` с наследниками (дрон/турель/босс), любой наследник должен подставляться туда, где ожидается `EnemyBase`, без спецпроверок на конкретный подтип со стороны вызывающего кода. Если для работы с конкретным врагом снаружи нужен `is`/`as`-каст к подтипу — это признак, что абстракция подобрана неверно (не хватает метода/свойства в базовом классе или интерфейсе).

### 1.4 Interface Segregation — маленькие интерфейсы под конкретную способность
`IDamageable` — правильный пример (один метод, одна способность "может получать урон"). При появлении новых сквозных способностей (например "можно подобрать", "можно оглушить", "реагирует на выстрел") — заводить отдельный узкий интерфейс под каждую, а не один большой `IEnemy`/`IInteractable` со всеми методами сразу. Компонент реализует ровно те интерфейсы, которые ему нужны.

### 1.5 Dependency Inversion — зависимость от абстракции, не от конкретного класса
Код урона обращается к `IDamageable`, а не к `EnemyController` напрямую — уже верно реализовано и должно оставаться нормой для новых систем. Где стыка ещё нет (например, будущий менеджер квестов/прогрессии) — компоненты должны знать о интерфейсе/событии, не о конкретной реализации другого компонента.

## 2. GRASP-паттерны, которые уже видны в проекте

- **Information Expert:** `SavePoint` сам решает, когда сохранять (у него есть коллайдер и он получает `OnTriggerEnter2D`) — не диспетчер извне пуляет "проверь точки сохранения". Держаться этого: логика живёт там, где есть данные для решения.
- **Creator:** `PlayerController` создаёт `Projectile` через `Instantiate` — он же инициирует выстрел и владеет позицией спавна, это корректно (Creator = тот, кто использует/содержит/тесно работает с создаваемым объектом).
- **Controller (UI-паттерн, не GRASP, но рядом):** `PauseMenuController`/`MainMenuController`/`AmmoHUD` как singleton-контроллеры экрана/HUD — рабочий прагматичный паттерн для этого масштаба проекта, оставляем как норму для новых HUD/меню-экранов (см. 3.3 про границы применения).

## 3. Правила декомпозиции (конкретно для Unity)

### 3.1 Данные — не хардкодить, выносить в сериализуемые поля/ассеты
Уже стандарт в проекте (`[SerializeField] private float jumpForce`), но есть известная ловушка: значения запекаются в сцену/префаб при первом добавлении компонента, и правка дефолта в коде их не перезаписывает (см. инцидент с `jumpForce`/`projectileSpeed` в технических заметках). Правило: для параметров, которые точно будут тюниться (урон, скорость, кулдауны, HP), по мере роста числа врагов/оружия переходить на **ScriptableObject-конфиги** (`EnemyStats`, `WeaponStats`) вместо полей прямо на компоненте — тогда один ассет данных переиспользуется на много префабов и не расползается по сериализованным сценам.

### 3.2 Один GameObject — несколько узкоспециализированных компонентов
**Выполнено (2026-07-28):** `PlayerController` (380 строк) разбит на 4 компонента на GameObject `Player`:
- `PlayerMovement` — бег/прыжок/дэш, владеет `Rigidbody2D`, публикует `FacingDirection`/`IsGrounded`/`IsDashing` для остальных.
- `PlayerCombat` — ближний/дальний бой, кулдауны, боеприпасы. Требует `PlayerMovement` на том же объекте (`[RequireComponent]`), читает у него `FacingDirection`/`IsGrounded`, дёргает `SetMovementLocked(true/false)` на время наземного удара мечом.
- `PlayerHealth` — HP, реализует `IDamageable`.
- `PlayerInputHandler` — реализует `InputSystem_Actions.IPlayerActions`, переводит колбэки Input System в вызовы методов на `PlayerMovement`/`PlayerCombat` (роль "Controller" в GRASP: единственная точка, транслирующая внешние события в вызовы на доменные объекты). Названа `PlayerInputHandler`, не `PlayerInput` — так называется встроенный класс `UnityEngine.InputSystem.PlayerInput`, совпадение имён даёт неоднозначность компиляции.

Правило на будущее: компоненты на одном GameObject получают друг друга напрямую через `GetComponent<T>()` в `Awake()` (не через сериализованные ссылки) — просто и без лишней настройки в инспекторе. Кросс-объектная развязка (например, HP игрока → HUD) идёт не через прямые ссылки, а через Event Bus (см. 3.5).

### 3.3 Singleton — только для по-настоящему единственных в сцене менеджеров, управляемых императивно
`PauseMenuController.Instance`, `SaveSlotMenuController.Instance` — нормальная практика: это императивные действия ("открой панель", "поставь на паузу"), а не оповещение о смене состояния, вызывающий код явно хочет вызвать конкретный метод на конкретном единственном менеджере экрана.

**Уточнение (2026-07-28):** `HealthHUD`/`AmmoHUD` **больше не Singleton** — раньше пушились через `.Instance?.SetHealth(...)`, теперь подписываются на Event Bus (см. 3.5). HUD, который только *реагирует* на изменение состояния (а не выполняет команду), не нуждается в глобальном доступе — он сам решает, на что подписаться (Information Expert: HUD знает, что ему показывать, и сам получает данные).

**Не** превращать в Singleton игровые сущности, которых может быть много (враги, снаряды, точки сохранения) — там ссылки должны передаваться явно (компонент на объекте, параметр метода), а не через глобальный доступ.

### 3.4 Враги — общий контракт с первого же второго типа врага
**Выполнено (2026-07-28):** второй враг (`FlyingDroneController` — летающий боевой дрон с дальней атакой) появился, и по этому же правилу общий контракт вынесен **сразу**, не откладывая:
- `EnemyHealth` — вынесенный из `EnemyController` компонент: HP, `IDamageable`, смерть (отключает коллайдер, триггерит Death-анимацию, `Destroy(gameObject, deathDuration)`). Оба врага (`EnemyController` — наземный, ближний бой; `FlyingDroneController` — летающий, дальний бой) используют его как `[RequireComponent]`-сосед, а не через наследование — **композиция, не абстрактный базовый класс** (сознательный выбор: в проекте уже есть устоявшийся паттерн "GameObject + несколько узкоспециализированных компонентов", см. 3.2 про Player; заводить параллельно ещё и классовую иерархию наследования было бы двумя разными способами decomposition ради одной и той же цели).
- Оба врага читают/пишут `EnemyHealth.IsDead` вместо собственного поля `isDead` — единственный источник правды о том, жив ли враг.
- `FlyingDroneController` переиспользует существующий `Projectile.cs` для своей дальнобойной атаки (тот же класс, что у игрока — он уже был написан достаточно обобщённо: не завязан на то, кто стрелял, кроме параметра `owner` для самоисключения). Отдельный `EnemyProjectile.prefab` — тот же `Projectile`, только перекрашенный спрайт (визуально отличать вражеские снаряды от игровых), новый класс не понадобился.
- Наземный `EnemyController` и летающий `FlyingDroneController` НЕ имеют общего базового класса поведения (патруль/погоня/атака) — это осознанно: их логика движения/атаки достаточно разная (наземный ходит по X и бьёт в упор, дрон летает в 2D и держит дистанцию для стрельбы), общий код был бы либо тривиальным, либо вынужденной абстракцией ради абстракции. Если появится третий враг с поведением, ощутимо похожим на один из двух существующих — тогда выносить общее.

### 3.5 Event Bus — для развязки между системами, не для всего подряд
**Выполнено (2026-07-28):** `EventBus.cs` — статический типизированный pub/sub (`Subscribe<T>`/`Unsubscribe<T>`/`Publish<T>`, диспетчеризация по `Type` события, без завязки на конкретных издателей/подписчиков — GRASP Pure Fabrication: класс не из предметной области игры, придуман исключительно ради low coupling). Payload-события — простые `readonly struct` в `GameEvents.cs` (`PlayerHealthChanged`, `PlayerAmmoChanged`).

**Когда использовать Event Bus, когда — прямую ссылку:**
- Компоненты на одном GameObject (Movement/Combat/Health/Input игрока) — **прямая ссылка** через `GetComponent<T>()`. Они и так неразделимо связаны (существуют только вместе), развязка через шину добавила бы косвенность без пользы.
- Издатель не знает и не должен знать, кто слушает, либо слушателей несколько/они будут появляться (HUD, будущие системы прогрессии/звука/аналитики, реагирующие на HP/урон/смерть) — **Event Bus**. Подписка в `OnEnable`, отписка в `OnDisable` (обязательно — иначе утечка подписки на уничтоженный объект).
- Не заводить событие "про запас" без реального второго подписчика — на 2026-07-28 через шину идут только `PlayerHealthChanged`/`PlayerAmmoChanged` (у обоих есть подписчик — HUD). Новые события (смерть врага, пауза, сохранение) добавлять, когда появится реальный слушатель, а не заранее.

### 3.6 Предметы/инвентарь — ScriptableObject-данные + узкие компоненты
**Выполнено (2026-07-28):** `ItemDefinition` (ScriptableObject, `Assets/Data/Items/*.asset`) — база: имя, описание, иконка, флаг `stackable`. `WeaponDefinition : ItemDefinition` добавляет тип (ближний/дальний) и урон — конкретный пример правила 1.2 (Open/Closed): новое оружие/предмет = новый `.asset`-файл, не новая ветка кода. Сейчас заведено два ассета (`Sword`, `Pistol`), их данные (урон и т.п.) для геймплея пока не читает `PlayerCombat` — это дублирование значений до следующей итерации (см. открытые вопросы).

- `PlayerInventory` — компонент на `Player` (та же схема, что Movement/Combat/Health/Input), хранит `List<InventoryEntry>`, публикует `InventoryChanged` через Event Bus при изменении (см. 3.5) — реальный подписчик уже есть (`InventoryMenuController`).
- `ItemPickup` — триггер-компонент для будущих подбираемых предметов в уровне (инфраструктура готова, в сцене пока не размещён — по аналогии с `IDamageable` до появления врагов, см. §0/1.2).
- UI (`InventoryMenuController`) — отдельная вкладка внутри паузы (аналогично `SaveSlotMenuController`: сама панель — сиблинг `PausePanel` на `Canvas`, взаимоисключающий показ). Список предметов строится динамически (`Instantiate` по шаблону `itemButtonTemplate`) из `PlayerInventory.Entries`, а не жёстко прописанными кнопками — так система выдерживает рост числа предметов без правки UI-кода.
- **Взаимодействие панелей паузы:** т.к. вкладка инвентаря открывается ВНУТРИ уже активной паузы (не отдельный `Time.timeScale`), `PauseMenuController.Resume()` явно закрывает инвентарь (`inventoryMenu?.ForceClose()`) — иначе возможен баг "инвентарь остался на экране, а игра уже разморожена" (тот же класс проблемы, что описанный ранее известный edge-case с SaveSlot, но здесь пофикшен, а не оставлен).

## 4. Открытые вопросы (для следующих итераций)

- `WeaponDefinition.Damage`/`WeaponType` пока не используются `PlayerCombat` (там свои `meleeDamage`/`rangedDamage` поля) — свести к одному источнику правды (`PlayerCombat` читает урон из `WeaponDefinition` через `PlayerInventory`) или осознанно оставить как есть, пока оружия не переключаются игроком в рантайме.
- ScriptableObject-конфиги для врагов (`EnemyStats`: HP/урон/скорость вместо полей на компоненте) — вводить сейчас или дождаться третьего типа врага. Пока и `EnemyController`, и `FlyingDroneController` держат баланс прямо в `[SerializeField]` на компонентах — двух врагов достаточно мало, чтобы дублирование ещё не болело.
- Правила именования и структуры для будущих систем (progression, диалоги — если появятся).

**Решено (2026-07-28):**
- Событийная система → Event Bus для кросс-системной развязки (HP/патроны/инвентарь → HUD/UI), прямые ссылки — для компонентов на одном GameObject. См. 3.5.
- Разделение `PlayerController` → сделано, 4 компонента (`PlayerMovement`/`PlayerCombat`/`PlayerHealth`/`PlayerInputHandler`). См. 3.2.
- ScriptableObject-конфиги для предметов/оружия → введены (`ItemDefinition`/`WeaponDefinition`), см. 3.6.
- Общий контракт врагов → `EnemyHealth` (композиция, не наследование), второй враг (`FlyingDroneController`) добавлен по этому контракту. См. 3.4.
